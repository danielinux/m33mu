# ADR-001: primary circuit solver

**Status:** Open. No solver has passed the live firmware-coupling gate.  
**Date:** 2026-10-23

## Context

The workbench requires deterministic transient stepping with source changes during a run, state preservation, worker yielding, pause/resume, and event localization at MCU input thresholds. A completed batch `.tran` result is insufficient because firmware GPIO writes and circuit voltages must share virtual time.

## Evidence so far

- The public `eecircuit-engine` TypeScript API (`eelab-dev/EEcircuit-engine` at `75594eec516be3087e64eeb5347a958de70f410c`, MIT) exposes `setNetList()` and `runSim()`. Its implementation runs `source test.cir`, `destroy all`, `run`, and then reads `out.raw`. There is no public incremental step/source-update API. **Reject this wrapper as-is** for the live workbench; the underlying WASM core could be reconsidered only after an incremental control API and its license/model provenance are demonstrated.
- CircuitJS1 at `778723096a46f3c5ce4e11bd9edc24324754f02c` is GPL-2.0-or-later. `SimulationManager.runCircuit()` performs `startIteration()`, element `doStep()`, matrix solve, `stepFinished()`, and `app.onTimeStep()`, but it loops according to `Date.now()`, speed controls, frame limits, and `app.simRunning`. It calls back into `CirSim`, and `CirSim.onTimeStep()` updates scopes and hooks. `CircuitMatrix` is a plausible numerical component, but no single-quantum headless API or mid-transient source-update test has been produced. It needs a bounded-step extraction before it can be evaluated for the worker; it is not selected.
- A newer public TypeScript port, `noiseweaver/Perun` at `067d1c9c59e27f72f6498ec224f3735d0da6364a`, separates a no-DOM `Simulation` engine. Its `packages/engine/src/Simulation.ts` header identifies GPL-2.0-or-later and says it ports CircuitJS1's TypeScript engine at `7ec858d662d8be1d76d54241ba3a5c1d1c524f51`, checked against upstream Java `SimulationManager` at `5a707168778216bb6ed01bfdd62e8bbf7ae0a032`. `Simulation.step(n)` synchronously runs a requested count of transient steps and returns the count completed; `setElements()` retains the element objects while flagging re-analysis. In an isolated `/tmp` checkout at the pinned Perun commit, `pnpm --filter @perun/engine typecheck` passed and `pnpm exec vitest run tools/golden/src/next.test.ts` passed 132 fixture tests. A temporary RC probe changed a DC source from 5 V to 0 V mid-run, forced re-analysis, confirmed capacitor voltage remained continuous across the first 5 us step and then discharged, confirmed pause stopped after one step and resume advanced again, and localized the 1 V RC crossing to within one 5 us solver quantum. The probe files and dependency checkout are outside this repository; no solver code was imported. This establishes a credible deterministic incremental candidate, but not firmware GPIO/EXTI coupling, nonlinear device parity for this workbench, worker yielding under a budget, or complete license compatibility. Keep selection open pending those checks.
- Preliminary license graph inspection at the same Perun revision found that `packages/engine/package.json` declares no runtime package dependencies and all imports reachable from `packages/engine/src/index.ts` resolve to engine-local files. The engine is GPL-2.0-or-later. Four sparse-matrix files are additionally marked `GPL-2.0-or-later AND Apache-2.0` and attribute EJML/Peter Abeles; their inline notices cite Apache-2.0, but a complete redistribution notice/source audit is still required. Choosing GPLv3 for the Perun component appears compatible with this repository's AGPL-3.0-or-later under AGPLv3 section 13, subject to preserving applicable licenses/notices and checking the final combined distribution. This is preliminary compatibility analysis, not adoption clearance or legal advice.
- A local native ngspice Shared Library experiment did not produce a valid transient waveform. Follow-up against Debian `libngspice0` **47+ds-1** using its installed shared library and ctypes callback bindings isolated two failures: (1) with `Vstim in 0 dc 1 external`, `ngSpice_Init_Sync()` returns success and the sync callback runs, but the registered voltage callback is never called and both source and RC node remain at 0 V; (2) capping the sync callback's transient delta at 10 us produces `Timestep too small` at the 100 us stop time. Without the sync callback, the transient finishes but still returns a zero waveform. No ngspice development headers are installed, and an Emscripten build has not been demonstrated. The installed runtime therefore cannot currently support the required live-source/coupling contract; this does not prove the upstream API is incapable when correctly built and driven.
- A reproducible staged firmware-to-firmware coupling probe captures PA5 from `test-stm32h5f4-signal-output-timing` after `signal_trigger_marker()`, feeds those transitions into a Perun 1 kOhm/10 nF RC (3.3 V, 5 us step), and replays the first four 1775/1525 mV crossings through `test-stm32h563-signal-exti-both`. Run `scripts/run-web-coupling-probe.sh /path/to/pinned/Perun` with the Perun checkout at `067d1c9c59e27f72f6498ec224f3735d0da6364a`; the script builds both firmware fixtures, records output, runs the engine probe, regenerates `web/fixtures/solver/perun-firmware-coupling.json`, checks analytic timing and runs the `.sigc` replay. The current capture has edges at 47.203, 94.438, 141.672, 188.906, 236.141 and 283.375 us; crossings are at 60.465, 105.343, 155.397, 200.343, 250.397 and 295.343 us. Replay reaches BKPT `0x7f` after 12,896 virtual cycles. Against the continuous analytic RC response, using interpolated capacitor voltage at each source edge, absolute timing errors are 5.543, 3.330, 6.121, 3.871, 6.658 and 4.412 us (maximum 6.658 us). Source changes are applied at the next 5 us solver boundary and the coarse trapezoidal integration adds numerical error; this records the staged error but does not establish an acceptable shared-clock worker tolerance. The reproducible probe and firmware/circuit passes are sequential, so this does not establish live feedback or worker yielding.

## Decision

Defer selection. Do not wire firmware GPIO into an assumed ideal voltage source. The isolated Perun/CircuitJS spike now passes pinned reference fixtures, bounded stepping, RC source-update/state-continuity, pause/resume and one-quantum threshold localization probes. The staged firmware-output -> Perun RC -> firmware EXTI path reaches its expected breakpoint, and the RC crossings have been compared with an analytic response (maximum absolute error 6.611 us for a 5 us solver quantum and boundary-quantized source updates). This establishes a staged proof with measured error, not a live shared-clock co-simulation or a worker-level tolerance. Preliminary source-level review suggests the engine's declared runtime dependency set is empty and a GPLv3 choice may combine with this AGPLv3 project, but sparse-matrix Apache notices and complete final-distribution provenance remain to be checked. Next make the probe reproducible, establish a shared clock and bounded worker loop, and test representative divider/diode/BJT behavior and suitable numerical tolerances. Separately pursue a reproducible ngspice Shared Library WASM build/control spike. Select one only after the same divider, RC, diode, BJT, and GPIO/RC fixtures pass documented numerical and causal-ordering checks.

## Required evidence to close

1. Mid-transient source changes without resetting unrelated reactive state.
2. A controllable simulation quantum, bounded worker execution, pause/resume, and deterministic replay.
3. Firmware output edge -> analog RC threshold crossing -> GPIO/EXTI event with ordering and timing tolerance measured against a reference fixture.
4. Numerical fixture comparisons, solver build ID, license notices and complete model/dependency provenance.
